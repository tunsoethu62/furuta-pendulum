## Why v2.4 changes only the catch

The nonlinear simulator holds this exact catch state, and plant variants tried
(weaker coupling, motor lag, more friction near upright) do not reproduce the hardware
fall exactly, so the cause is not identified. In every variant, though, the
failures share the same signature as the hardware: arm speed pinned at 180 deg/s.
A balanced on this hardware with the older 100 rad/s^2 / 360 deg/s build
(`docs/BALANCE_TEST_2026-11-04.md`), and the motor ran the 300 deg/s pump in this run.

**v2.4:** for the first 1 s after an automatic catch, A uses 100 rad/s^2 / 360 deg/s;
afterwards the speed limit ramps down at 60 rad/s^2 until it is back at the proven
60 rad/s^2 / 180 deg/s, so the commanded velocity never jumps. Gains, trim, the
25-degree drop (driver off) and capture gates are unchanged. Balance entered any
other way (parity tests) never uses the catch limits.

Simulated catches from d = 10..18 deg, inward rate 0.2..1.0 x separatrix speed,
arm -20..+20 deg, encoder offset -1..+1 deg (375 states each):

| Plant | v2.3 held | v2.4 held |
|---|---|---|
| nominal (near-top friction 0.02) | 351 | 374 |
| near-top friction 0.05 | 251 | 374 |
| coupling x0.8 + 20 ms motor lag | 202 | 338 |

The worst held cases use up to about 85 deg of arm travel (hard cutoff 89 deg):
arm travel becomes the next limit, and an ARM stop (driver off) is the expected
failure mode if the catch needs more room.

All host checks pass (new catch-phase tests: catch limits apply only after a moving
catch, per-tick velocity change bounded, forced ramp-down, return to exact balance
limits). Builds: swingup 20,304 B flash / 1,080 B RAM; balance 9,432 / 469;
balance.ino unchanged. **Not hardware-tested.**
